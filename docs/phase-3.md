# Phase 3: technical overview and OKF

Historical record: the deterministic purpose heuristics described below were removed by the architecture rework. See [current verification](rework-verification.md) for the implemented synthesis and question pipeline.

Status at the initial 2026-09-25 review: experimental implementation, M3 incomplete. The purpose heuristics failed live quality checks, including promoting generic terms such as “address” and “hello.” The [architecture rework](architecture-rework.md) defined their removal and replacement with source-grounded synthesis. The description and verification below record that earlier implementation; passing its structural checks did not establish that its explanations were correct.

Phase 3 creates a deterministic onboarding overview when a GitHub snapshot finishes indexing. It works in the default strict-local profile without a model provider. The overview is a bounded starting map of explicit source declarations and resolved static relationships, not a full behavioral interpretation. It is loaded before search in the UI. The existing source viewer resolves every overview citation against the selected snapshot.

The generator reads the complete artifact inventory and records exactly one category for every path, including excluded, unsupported, failed, pending, and unclassified artifacts. The UI exposes the full inventory in pages. Pending or failed analysis marks the overview partial. For purpose, it examines analyzed implementation files throughout the repository for UI, server/API, smart-contract, and data roles using source types, conventional entry-file names, and declared dependencies. A technical-scope statement requires at least two distinct cited files and is marked as a partial inference. It says the repository contains those code areas, without assuming they are one deployed product. It also samples first source chunks across up to 500 approved files using hash ordering, so an alphabetically early folder does not dominate. Repeated implementation identifiers across at least three files in two source areas can add a tentative domain-focus inference with citations to the exact code chunks; the cap and the inference label remain visible limits. This works without a README or prescribed directory layout. An explicit introductory sentence from the root README, or a root `package.json` description, can add an attributed documentation claim, but is never the sole required source. A README heading, code-fence comment, or nested component README title cannot establish the repository's purpose. If the available files are too sparse, purpose remains unresolved; code roles and recurring identifiers alone still leave the specific product or business purpose unresolved. The generator also samples launch/build manifests, Go main functions and packages, SQL files, and resolved Go or imported SCIP relations. It distinguishes a declaration from an observed execution, does not infer a deployment from a library-only source tree, and keeps unavailable runtime configuration unresolved. Other languages remain searchable and citable but do not gain fabricated parser depth. A capped set of 80 cited claims keeps the landing overview readable; the inventory and search retain the rest of the source scope.

Overview claims have stable IDs and validated snapshot-scoped evidence IDs. The generator checks the inventory totals, claim references, and privacy policy before publication. A fingerprint of the snapshot commit, artifact statuses and hashes, evidence hashes, symbol IDs, relation IDs, and generator version controls regeneration. Prior overview versions remain in PostgreSQL. Local correction notes attach to claim IDs, survive regeneration, and are marked orphaned if a changed overview no longer contains the claim. They are not treated as source evidence or human verification. A correction can be removed. The overview and export APIs enforce the same local session and repository/snapshot boundary as search.

The OKF ZIP has a root `index.md` with `okf_version: "0.2"` and one UTF-8 Markdown concept under `concepts/` per overview area. Concept frontmatter carries `type`, `title`, `description`, `status: draft`, a deterministic process actor and application-supplied generation timestamp, plus `sources` entries for cited evidence. Each factual line has a keyed footnote matching a `sources[].id`. Source URLs point to the captured immutable GitHub commit and line range. The renderer uses the pinned [OKF v0.2 specification revision](https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/0b87c52c6ef999286c745e19998fdfcd03d5dbee/SPEC.md). It does not invent human review, copy raw repository content, or include local correction notes. Each concept passes the privacy scan before ZIP creation.

The API adds `GET /overview`, `GET /overview/inventory?offset=&limit=`, `POST /overview/notes`, `DELETE /overview/notes/{noteId}`, and `GET /knowledge/export` under a ready snapshot path. A new capture generates the overview as part of its durable job. Opening an older ready snapshot lazily builds or refreshes the overview. SCIP import triggers a refresh when possible; a later overview request also repairs stale fingerprints. The ZIP is at most 2 MiB.

All baseline prompts A00 and P00–P11 are present as exact UTF-8 files in the packaged registry with versions, checksums, schema references, allowed-tool lists and token/call ceilings. The binary validates the registry before serving. The generic scoped input/output envelopes are packaged as JSON Schemas. No model prompt is executed in Phase 3; task-specific model output validation and evaluations are prerequisites for enabling that path later.

Verification: `go test ./...`, `go vet ./...`, the frontend production build, `python scripts/check_phase0.py`, Compose build and `doctor`, the Phase 1 capture smoke, and `scripts/smoke_phase3.ps1`. Unit fixtures check a library-only overview for invented deployment, reject a claim with an unknown evidence ID, verify OKF source footnotes and lack of human verification, and distinguish a static Go call or Dockerfile declaration from executed behavior. The Phase 3 smoke checks inventory accounting, every rendered citation, concept files, cross-repository 404s, and correction persistence through reindex/removal using a public GitHub snapshot. The overview and OKF remained available after a PostgreSQL restart. A separate public Go snapshot generated a 79-claim overview across ten sections, and its ZIP passed the OKF validator.

Remaining limits: the overview is a conservative deterministic map. It does not synthesize a complete user journey, establish cross-language execution paths, identify every runtime unit, verify deployment, or answer interactive questions. For a repository without supported launch evidence, those areas remain empty with explicit limitations. Broad component/flow synthesis, deeper language adapters, model-backed claim assessment, and technical chat are later work. A normally generated SCIP file that omits optional embedded document text is still not accepted by the current Phase 2 importer; this compatibility gap should be resolved before relying on SCIP for general-language graph coverage.
